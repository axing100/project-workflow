# Project Workflow 主动多智能体调度引擎设计

## 一、目标

将现有“多智能体治理协议”升级为可主动选择执行拓扑、创建 Worker、按依赖波次调度、持久化任务分配并验证交付的执行引擎，同时保留方案确认门禁、Git 权限边界和跨任务恢复能力。

## 二、范围

### 范围内

- 规划阶段为复杂任务选择 `AUTO_MULTI_AGENT`、`SINGLE_AGENT` 或 `MANUAL_MULTI_AGENT`。
- 将执行模式、最大 Worker 数、拓扑和任务依赖图写入持久化记录。
- 为任务记录依赖、写入范围、是否可委派、状态、Owner、尝试次数和证据。
- 执行阶段在运行时提供子智能体工具且计划已确认时主动创建 Worker。
- 按 dependency-ready 和写入范围互斥规则形成执行波次。
- 持久化分配、完成、释放和阻塞状态，支持重启、压缩和中断恢复。
- 统一 Worker 输入、交接、验收、失败重试、串行降级和最终集成流程。
- 更新中英文文档、插件元数据、测试和本机安装缓存。

### 范围外

- 实现或替代 Codex 运行时自身的子智能体 API。
- 绕过系统、开发者、仓库或用户权限限制。
- 自动授权提交、推送、部署、破坏性操作或生产访问。
- 允许多个 Worker 修改重叠写入范围、规范计划文件或执行竞争性 Git 操作。
- 保证所有 Codex 版本、模型或运行环境都提供相同并发槽位。

## 三、现状与约束

- `plan` 已能拆分依赖感知、接近提交粒度的任务，但多智能体字段主要是自然语言约定。
- `execute` 仅要求委派前读取多智能体参考，没有主动调度循环。
- `multi-agent-orchestration.md` 已定义拓扑、Owner、写入互斥、交接和集成规则。
- `workflow_state.py` 只管理计划审批和阶段，不管理任务 DAG 或 Worker 生命周期。
- 当前运行时最多可用槽位由宿主决定；根协调者本身占用一个槽位。
- 当前工作树已有上一轮确认的 `index/SKILL.md` 准入规则修改，实施时必须保留。
- 基线为 7 项单元测试通过，三个技能和插件 validator 通过。

## 四、总体架构

```text
Project Workflow Plan
        │
        ├─ 生成设计、Markdown 实施计划
        └─ 生成 companion orchestration JSON
                    │
                    ▼
          用户确认具体 revision
                    │
                    ▼
Project Workflow Execute（协调者）
        │
        ├─ workflow_state.py 校验审批门禁
        ├─ orchestration_state.py 计算 ready tasks 和互斥约束
        ├─ 运行时 collaboration tools 创建/跟进/等待 Worker
        ├─ 验收 Worker handoff、diff 与测试证据
        └─ 更新状态，推进下一 wave，最终集成和交付
```

技能层负责需要语义判断的工作：任务拆分、是否适合并行、Worker 提示、验收与重新规划。状态脚本负责确定性工作：schema 校验、依赖就绪、写入冲突、合法状态迁移、尝试次数和原子写入。

## 五、持久化模型

### 5.1 计划执行字段

实施计划 frontmatter 增加可选字段：

```yaml
execution_mode: "AUTO_MULTI_AGENT"
max_workers: 3
agent_topology: "SHARED_WORKSPACE"
orchestration_state: "docs/plan/NNN-任务.orchestration.json"
```

旧计划缺少这些字段时保持兼容，按 `SINGLE_AGENT` 执行。

### 5.2 Companion JSON

新增 `project-workflow/orchestration/v1` JSON 状态，至少包含：

- `plan_id`、`revision`、`execution_mode`、`max_workers`、`topology`；
- 任务的 `id`、`status`、`depends_on`、`write_scope`、`agent_eligible`；
- 运行字段 `owner`、`started_at`、`attempts`、`evidence`、`block_reason`；
- schema 版本和更新时间。

任务状态使用 `PENDING`、`ASSIGNED`、`COMPLETED`、`BLOCKED`。协调者只有在验收交接和证据后才能写入 `COMPLETED`。

### 5.3 状态脚本接口

新增 `scripts/orchestration_state.py`，提供：

- `validate`：校验 schema、plan ID/revision、依赖存在性、循环依赖、写入范围和模式；
- `ready`：以 JSON 输出依赖已满足且未与活动任务冲突的候选任务；
- `assign`：校验合法性后绑定 Owner、时间并增加尝试次数；
- `complete`：要求非空验收证据后完成任务；
- `release`：Worker 失败或取消后释放为待调度状态；
- `block`：记录不可自动恢复的阻塞原因；
- `inspect`：输出规范化状态。

所有修改使用临时文件加原子替换，仅依赖 Python 标准库。

## 六、主动调度算法

1. 协调者重新读取设计、计划、Git 和 orchestration state。
2. 校验计划审批、revision 和执行模式。
3. `SINGLE_AGENT` 直接使用现有串行规则。
4. `MANUAL_MULTI_AGENT` 只调度计划中已显式分配的任务。
5. `AUTO_MULTI_AGENT` 在运行时工具可用时：
   - 取得 ready tasks；
   - 排除不可委派、共享关键文件和重叠写入范围；
   - Worker 上限取计划上限、运行时剩余槽位和 ready task 数的最小值；
   - 为每个 Worker 发送固定任务契约并持久化 Owner；
   - 等待交接，验收后完成或退回；
   - 推进下一执行 wave。
6. 没有子智能体能力、可并行任务不足或协调成本过高时，自动降级为串行并记录原因。

根协调者不把创建 Worker 的权限扩大为提交、推送、部署或破坏性操作权限。

## 七、Worker 契约

每个 Worker 必须收到任务 ID、目标、范围外内容、依赖状态、精确写入范围、验收标准、验证命令、适用规范和计划链接，并遵守：

- 不修改规范设计、计划、交付报告或 orchestration state；
- 不执行 Git 提交、推送、分支切换或破坏性操作；
- 不扩展架构、接口或任务范围；
- 发现冲突或重大变更时停止并报告；
- 返回路径、行为、测试、偏差、风险和补丁/工作树状态。

## 八、失败、恢复与重新确认

- 交接不完整：协调者向原 Worker 补充一次明确请求。
- 第二次仍不满足：释放任务并由协调者接管或重新分配。
- 写入冲突或共享环境争用：停止相关并行任务，转为串行。
- Worker 异常终止：释放 Owner，保留尝试计数和已有工作树证据。
- 达到重试上限：标记 `BLOCKED`，记录所需输入或状态变化。
- 架构、接口、数据模型、安全或范围发生重大变化：中断受影响 Worker，提升 plan revision，清空批准并重新请求确认。
- 重启或上下文压缩：从计划、JSON 状态、Git 和活动 Agent 列表重建调度状态，不依赖记忆。

## 九、兼容性与安全

- 旧计划默认单智能体，不要求补建 JSON。
- 子智能体工具不可用时正常降级，不把插件判为失败。
- 共享工作区默认严格分离写入范围；关键共享文件只能由协调者或单一串行 Owner 修改。
- Worker 不接收超出任务所需的凭据或生产权限。
- 计划确认只授权计划内的子智能体委派，不推导提交、推送和外部写权限。
- 插件仍是行为和状态一致性层，不是安全沙箱；高优先级运行时约束始终优先。

## 十、可观测性、发布与回滚

- 计划记录执行模式、拓扑、最大 Worker、waves、Owner 和降级原因。
- JSON 记录任务状态、尝试和时间；交付报告记录实际并行度、失败和集成结果。
- 版本升级为 `0.3.0`，中英文 README 增加自动调度使用方式和限制。
- 本机用官方 cachebuster 流程重装，源码 manifest 最终保持 `0.3.0`。
- 回滚时恢复变更前技能、参考、脚本、测试和 manifest；旧单智能体计划仍可继续使用。

## 十一、权衡与成功标准

采用 companion JSON 会增加一个持久化文件，但能避免从自由格式 Markdown 推导调度状态的脆弱性。调度决策仍由模型负责，以避免用文件数量等粗糙指标替代语义判断。

成功标准：

- 已确认的 AUTO 计划能在运行时允许时主动创建不超过上限的 Worker。
- 依赖未满足、写入范围冲突或不可委派任务不会并行。
- Worker 失败可释放、重试、降级或阻塞，状态可在重启后恢复。
- 重大变更仍触发重新确认。
- 旧计划和单智能体模式保持兼容。
- 状态脚本、技能和插件验证全部通过，文档与实际行为一致。
