# Project Workflow v0.4.0 设计

## 1. 背景与问题

本版本针对 v0.3.0 冒烟测试、复杂任务 A/B 对照及实际会话中暴露的问题进行收敛优化。现有版本已经能够调用 Codex 原生子智能体并展示原生会话组件，但仍存在以下短板：

1. 技能文档与辅助脚本的命令契约容易漂移。模型曾把位置参数写成 `--to`，产生可恢复但影响体验的错误。
2. 插件路径缓存失效时会向用户播报内部定位过程，暴露实现细节并打断工作流叙事。
3. 规划阶段未统一预检 Python 版本、插件根目录、状态目录写权限和原生智能体可用性。
4. 当前工作流对中等任务和高风险任务采用近似相同的文档、检查与调度强度，固定成本偏高。
5. 多智能体更多按“可拆分”判断，尚未显式评估关键路径收益与协调成本。
6. 验收主要验证正常路径，对极值、时钟、幂等、迁移中的孤儿运行态等风险覆盖不稳定。
7. 测试型子智能体容易受实现上下文影响，缺少独立、对抗式的契约验证角色。
8. 计划中提前写入尚不存在的精确测试选择器，可能导致执行阶段先失败再纠正。

## 2. 版本目标

v0.4.0 聚焦“可靠、克制、可验证”：

- 提供稳定的生命周期复合命令，减少模型拼装状态迁移命令的机会。
- 提供一次性 `doctor` 预检，默认安静恢复插件路径，仅在确实阻塞时向用户报告。
- 引入 `LIGHT`、`STANDARD`、`FULL` 三档工作流强度，同时保持审批门禁不变。
- 引入收益门槛驱动的原生子智能体调度，默认最多并行两个 Worker。
- 将边界矩阵、迁移矩阵和独立契约验证纳入高风险任务的标准验收。
- 对文档中的可执行命令建立自动化契约测试。
- 保持既有 v0.3.0 计划与状态文件可读，避免强制迁移。

## 3. 非目标

- 不实现 Codex 客户端 UI 或自定义子智能体组件；插件继续使用原生智能体 UI。
- 不接入远程遥测、模型 API 或后台 Shell 伪造智能体。
- 不自动提交、推送、发布或部署用户仓库。
- 不在本版本实现完整的质量趋势仪表盘和跨项目统计。
- 不强制为所有任务启动子智能体。

## 4. 工作流分级

所有级别继续遵守“先规划、用户明确确认、再实施”的核心门禁。

### 4.1 LIGHT

适用于用户显式调用工作流、但改动范围局部且风险较低的任务：

- 设计可合并进实施计划，不要求独立设计文档。
- 默认单智能体执行。
- 仅要求基础验证、回归和交付摘要。
- 不要求独立契约验证 Worker。

### 4.2 STANDARD

适用于多模块改动、可并行实施但没有迁移或安全高风险的任务：

- 独立设计与实施计划。
- 在收益达到门槛时启用原生子智能体。
- 要求边界检查、回归验证和协调者只读验收。

### 4.3 FULL

适用于架构、迁移、兼容性、安全或长期协调任务：

- 包含 STANDARD 的全部要求。
- 存在持久化状态演进时必须提供迁移状态矩阵。
- 必须安排独立契约验证；验证者仅接收原始需求、公开契约和验收标准。
- 必须覆盖故障恢复、回滚与对抗性边界。

### 4.4 兼容策略

- 新计划使用 `workflow_profile` 字段。
- 未声明该字段的历史计划按 `FULL` 处理，以保持原有严格程度。
- `orchestration.json` 新字段均为可选字段，现有 schema 标识保持不变。

## 5. 生命周期命令契约

保留现有低层命令以兼容历史文档，同时新增稳定复合命令：

```text
workflow_state.py start-execution PLAN --confirmation TEXT
workflow_state.py complete PLAN
project_workflow_doctor.py --repo REPO [--json]
```

### 5.1 `start-execution`

单次完成以下原子语义：

1. 记录用户原始确认文本和时间。
2. 校验计划 revision 与当前批准 revision 一致。
3. 校验当前阶段允许执行。
4. 将阶段切换到 `IN_PROGRESS`。

失败时不得部分更新计划。

### 5.2 `complete`

仅在计划已经处于 `IN_PROGRESS` 且最终验收通过后切换为 `COMPLETED`。调度状态的 `--final` 校验仍由协调者先行执行，避免隐藏跨文件副作用。

### 5.3 文档命令契约

- 技能、README 中展示的生命周期命令必须来自同一份规范。
- 测试应验证参数解析、帮助文本和文档示例一致。
- 对执行时才能确定的路径使用明确占位符；不得把本机缓存版本路径写入公共文档。

## 6. Doctor 与安静恢复

`project_workflow_doctor.py` 检查：

- 插件源码根目录和清单版本。
- Python 版本及标准库能力。
- `workflow_state.py`、`orchestration_state.py` 的 CLI 契约。
- 仓库内计划、状态目录的可读写性。
- 计划 frontmatter 与调度状态 revision 的兼容性。
- 当前环境是否具备原生子智能体能力与可用并发槽位；无法检测时返回 `UNKNOWN`，不得伪造可用。

输出约束：

- 默认只输出一行人类可读结论。
- `--json` 输出稳定字段，便于测试和后续自动化。
- 插件缓存路径失效但能在本机唯一恢复时静默修复定位，不向用户播报内部搜索过程。
- 仅阻塞问题使用非零退出码；建议项不得阻断计划生成。

## 7. 收益门槛调度

任务可选声明：

- `estimated_minutes`
- `coordination_minutes`
- `critical_path`
- `role`
- `independent_verification`

协调者仅在以下条件同时满足时启动 Worker：

1. 至少存在两个可安全并行、写入范围不重叠的就绪任务；独立契约验证任务除外。
2. 预计节省时间大于协调成本，并达到默认 20% 的关键路径收益门槛。
3. Worker 数不超过计划与环境容量的较小值，默认上限为 2。

独立契约验证属于质量隔离任务，可以在单个任务就绪时单独启动，但不得与被验证实现共享写入范围。

## 8. 风险驱动验收

### 8.1 通用边界矩阵

STANDARD/FULL 任务应按实际接口选择以下维度，不要求机械覆盖无关项：

- 空值、布尔值与整数类型混淆。
- 负数、零、上界、超大整数和溢出。
- 重复项、未知项、大集合和顺序稳定性。
- naive 时间、非 UTC 时间、时钟回拨和时间溢出。
- 幂等重试、失败重试、部分成功和原子性。
- 原始异常泄漏、并发竞争和恢复路径。

### 8.2 迁移状态矩阵

涉及持久化状态升级时，FULL 计划必须枚举：

- 每个旧状态到新状态的映射。
- `RUNNING`、租约缺失、过期租约和孤儿任务的恢复策略。
- 不可识别状态的拒绝或隔离行为。
- 重复迁移、回滚和崩溃重入行为。

### 8.3 独立契约验证

- 验证者读取原始需求、公开接口和验收标准，不读取实现讨论或 Worker 的自我验收结论。
- 优先新增黑盒测试和失败用例，不直接修改生产实现。
- 发现问题后由原实现任务返工，验证者复验。

## 9. 稳定验证命令

计划中的验证命令分为：

- `DISCOVERY`：按目录、文件模式或测试发现运行，适用于测试尚未创建时。
- `EXACT`：精确到测试类或用例，仅在目标已存在并经过发现验证后使用。

规划阶段不得假设未来测试类名一定存在。执行阶段可以在创建后把 `DISCOVERY` 收紧为 `EXACT`，但必须先验证选择器有效。

## 10. 交互与错误呈现

默认只播报以下事件：

- 进入新的工作流阶段。
- 原生子智能体成功创建及其任务名。
- Worker 交接、失败回退和最终验收。
- 需要用户处理的阻塞问题。

自动恢复成功的路径查找、命令纠正和非阻塞建议写入内部证据，不单独占用会话消息。最终报告可在“诊断摘要”中简要列出。

## 11. 安全、回滚与版本

- v0.3.0 基线已由 Git tag `v0.3.0` 固化。
- v0.4.0 仅增加向后兼容字段和命令，不删除旧命令。
- 源码回滚以 `v0.3.0` 为依据；不得使用破坏性 Git 命令覆盖用户改动。
- 插件本机更新使用 cachebuster 与标准重装流程，避免继续命中旧缓存。
- 提交、tag、推送和远程发布均需单独授权。

## 12. 验收标准

1. 现有测试全部通过，历史计划在缺少新字段时仍可执行。
2. 生命周期复合命令具备原子失败测试，文档命令契约测试通过。
3. Doctor 在正常、缓存失效、不可写目录和不兼容 revision 下均有测试。
4. 三档工作流选择规则在技能和双语 README 中一致。
5. 调度器能拒绝低收益拆分，允许收益达标的并行任务，并支持独立验证例外。
6. FULL 模式能校验迁移矩阵和独立契约验证任务存在。
7. 公共文档不包含本机绝对缓存路径。
8. 插件清单更新为 `0.4.0+codex.<timestamp>` 并通过技能、插件验证。
