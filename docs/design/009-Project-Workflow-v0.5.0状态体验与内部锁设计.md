# Project Workflow v0.5.0 状态体验与内部锁设计

## 1. 背景与目标

当前 v0.4.1 将计划生命周期锁创建在计划文档旁边，形成 `docs/plan/.xxx.md.lock`；虽然它用于稳定的跨进程互斥且通常被 Git 忽略，但仍把插件内部实现暴露到了业务文档目录。

当前任务展示还把“代码是否实现”和“验收是否完成”压缩为 `[ ]`、`[~]`、`[x]`、`[!]` 一个维度。代码已经完成但数据库、压测或外部环境验收尚未完成时，任务只能继续显示为“进行中”，既不能准确反映编码进度，也容易在单智能体计划中产生多个 `[~]`。

v0.5.0 的目标是：

1. 用户文档只保留可读的设计、计划和交付内容，锁与机器状态统一进入 `.codex/project-workflow/<plan-id>/`。
2. 将任务拆分为“实现状态”和“验收状态”，分别统计实现进度和验收进度。
3. 用户可见状态使用固定符号加本地化文字，只支持简体中文与英语。
4. 机器状态作为唯一事实来源，计划文档状态由渲染器回写，插件不解析 Emoji 判断状态。
5. 保持 v0.4 计划可读，并提供显式、可审计、可回滚的迁移路径。

## 2. 范围

### 2.1 范围内

- 将计划锁、调度锁迁移到仓库内部状态目录；无显式仓库上下文的兼容命令使用用户私有临时锁目录，不再写入计划文档目录。
- 新增所有执行模式共用的任务状态文件 `.codex/project-workflow/<plan-id>/state.json`。
- 实现状态：未开始、实现中、已完成、已阻塞。
- 验收状态：未开始、验证中、部分通过、已通过、未通过、已阻塞、不适用。
- 整体展示阶段：规划中、等待确认、实施中、验收中、待交付、已完成、已阻塞。
- 固定状态符号：`⚪`、`🔵`、`🟡`、`✅`、`❌`、`⛔`、`➖`。
- 简体中文 `zh-CN` 与英语 `en-US` 两套资源；其他语言配置回退到 `en-US`。
- 新增原子任务状态命令，校验依赖、单智能体活动任务数、证据和合法转换。
- 在 Markdown 中使用受控标记块回写中文或英文展示，不把展示文本作为状态源。
- 对旧计划提供显式迁移和 Doctor 诊断；迁移前继续按 v0.4 规则读取。
- 更新技能说明、协议、README、命令契约、测试、安装验证和版本清单。

### 2.2 范围外

- 不支持中文、英语以外的语言包。
- 不翻译用户自己编写的任务标题、目标、证据和自由文本。
- 不修改 Codex 原生 UI、智能体图标或系统语言设置。
- 不引入数据库、网络服务、后台守护进程或模板引擎依赖。
- 不自动删除未知来源的历史锁文件，不自动迁移未确认的旧计划。
- 不执行 commit、tag、push、发布或生产安装；本机插件重装需单独明确授权。

## 3. 状态模型

### 3.1 内部任务状态

所有计划使用内部 `state.json` 保存稳定枚举：

```json
{
  "schema": "project-workflow/state/v1",
  "planId": "example-plan",
  "revision": 1,
  "displayLanguage": "zh-CN",
  "stateVersion": 1,
  "tasks": {
    "T01": {
      "implementationStatus": "COMPLETED",
      "verificationStatus": "PARTIAL",
      "implementationEvidence": ["代码和单元测试已完成"],
      "verificationEvidence": ["等待隔离环境压测"],
      "blockReason": null
    }
  }
}
```

`stateVersion` 在每次成功写入后递增，所有写命令支持期望版本 CAS。状态文件只保存工作流状态与证据引用，不复制设计和任务正文。

### 3.2 状态与符号

| 内部状态 | 中文显示 | 英文显示 | 符号 |
| --- | --- | --- | --- |
| `NOT_STARTED` | 未开始 | Not started | ⚪ |
| `IN_PROGRESS` | 实现中/验证中 | Implementing/Verifying | 🔵 |
| `PARTIAL` | 部分通过 | Partially passed | 🟡 |
| `COMPLETED` | 已完成 | Completed | ✅ |
| `PASSED` | 已通过 | Passed | ✅ |
| `FAILED` | 未通过 | Failed | ❌ |
| `BLOCKED` | 已阻塞 | Blocked | ⛔ |
| `NOT_APPLICABLE` | 不适用 | Not applicable | ➖ |

符号只承担视觉提示。渲染和状态机根据内部枚举工作，绝不根据 Emoji 或翻译文本反向推断状态。

### 3.3 Markdown 展示

任务正文保留用户内容，状态块由插件管理：

```markdown
<!-- project-workflow:task-status T01:start -->
- 实现状态：✅ 已完成
- 验收状态：🟡 部分通过
- 当前说明：等待隔离环境压测
<!-- project-workflow:task-status T01:end -->
```

英语计划渲染为：

```markdown
<!-- project-workflow:task-status T01:start -->
- Implementation status: ✅ Completed
- Verification status: 🟡 Partially passed
- Current note: Waiting for isolated performance testing
<!-- project-workflow:task-status T01:end -->
```

插件只替换受控标记块；用户正文、标题和证据原文不自动翻译。渲染重复执行必须幂等。

### 3.4 进度与整体阶段

计划摘要同时显示：

- 实现进度：实现状态为 `COMPLETED` 的任务数/总任务数。
- 验收进度：验收状态为 `PASSED` 或 `NOT_APPLICABLE` 的任务数/总任务数。
- 阻塞数：任一维度为 `BLOCKED` 的任务数。

展示阶段从生命周期与任务状态确定：

1. 生命周期为草稿或等待确认时显示规划中/等待确认。
2. 存在实现中任务，或仍有未完成实现时显示实施中。
3. 全部实现完成但仍有待验证、验证中、部分通过或未通过时显示验收中。
4. 全部适用验收通过但尚未完成最终门禁时显示待交付。
5. 生命周期完成后显示已完成。
6. 生命周期或任务存在阻塞且没有可继续任务时显示已阻塞。

实现完成不等于整个计划完成；只有最终门禁通过后生命周期才进入 `COMPLETED`。

## 4. 原子状态命令

新增统一任务状态工具，至少支持：

- 初始化或从计划创建任务状态。
- 开始实现、完成实现、阻塞实现。
- 开始验证、记录部分通过、标记通过、标记未通过、阻塞验证、标记不适用。
- 查看结构化状态和渲染后的摘要。
- 将状态幂等渲染回 Markdown。
- 显式迁移 v0.4 任务标记。

关键约束：

- `SINGLE_AGENT` 同时最多一个实现状态为 `IN_PROGRESS` 的任务。
- 任务依赖未满足时不能开始实现。
- 完成实现必须有实现证据；验收通过必须有验收证据。
- `FAILED` 与 `BLOCKED` 严格区分：前者是已执行并发现问题，后者是尚无法继续。
- 计划最终完成要求所有任务实现完成，且所有适用验收通过；`PARTIAL`、`FAILED`、`BLOCKED` 都不能通过最终门禁。
- 每次状态更新、Markdown 渲染和生命周期关联写入使用锁和 CAS，失败不产生半写状态。

## 5. 锁与文件布局

显式仓库上下文下的推荐布局：

```text
.codex/project-workflow/<plan-id>/
├── state.json
├── orchestration.json       # 仅多智能体计划
└── locks/
    ├── plan.lock
    ├── state.lock
    └── orchestration.lock
```

计划锁在尚未读取可信 plan ID 前，使用“仓库内计划相对路径的 SHA-256”确定稳定锁名；读取并验证 plan ID 后再进入相应状态目录。无 `--repo` 的历史兼容命令使用权限为 `0700` 的用户私有临时锁目录和绝对计划路径摘要，不再创建相邻锁文件。

锁文件保持稳定，不在每次解锁后删除，避免删除/重建造成不同进程锁住不同 inode。旧 `.md.lock` 只由显式清理命令在确认无旧版进程持锁后清理，不进行隐式删除。

## 6. 语言选择

仅接受：

- `zh-CN`
- `en-US`

选择顺序：用户明确选择 > 仓库语言规范 > 当前对话主要语言 > `en-US`。创建计划时由协调者把最终语言传给状态初始化命令并持久化；恢复执行时沿用，不随偶发对话语言改变。用户明确切换语言时只重渲染插件管理块，不翻译自由文本。

## 7. 兼容与迁移

| 旧状态 | v0.5 行为 |
| --- | --- |
| 新建 v0.5 计划 | 创建内部状态并渲染双状态块 |
| v0.4 `[ ]` | 显式迁移为实现未开始、验收未开始 |
| v0.4 `[~]` | 显式迁移为实现中、验收未开始，并提示人工确认歧义 |
| v0.4 `[x]` | 显式迁移为实现完成、验收通过，保留原 Evidence |
| v0.4 `[!]` | 显式迁移为实现阻塞、验收未开始，并要求补充阻塞原因 |
| 无内部状态的旧计划 | 继续按旧规则只读/执行；Doctor 给出非阻塞迁移建议 |
| 未知内部 schema/状态/语言 | 失败关闭，不降级或猜测 |
| 迁移中断 | 原计划和原状态不变，或完整新状态与渲染结果同时生效 |
| 重复迁移 | 幂等返回现有结果，不重复插入展示块 |
| 旧相邻锁 | 新版本不再创建；显式清理后不再出现 |
| 回滚到 v0.4.1 | v0.4.1 继续读取原计划正文；新增内部状态被忽略，迁移前备份可恢复旧展示 |

迁移不得根据 Evidence 自由文本猜测“编码已完成但验收未完成”。歧义状态必须保守映射并要求用户或执行者显式修正。

## 8. 安全与原子性

- 内部状态目录继续拒绝符号链接和仓库外路径。
- 状态、渲染和计划更新采用临时文件、原子替换和目录 `fsync`。
- 锁目录、文件模式和父目录可信性纳入测试。
- 不把翻译文本、Emoji 或 Markdown 排版作为权限、审批或完成门禁依据。
- 错误返回稳定非零退出码，不输出 traceback 或内部绝对缓存路径。

## 9. 验收与回滚

必须覆盖锁目录不污染 `docs/plan`、单智能体并发约束、双状态合法/非法转换、证据门禁、中英渲染、语言回退、幂等渲染、v0.4 迁移、损坏状态、CAS 冲突、最终完成门禁和全量回归。

回滚采用 Git 差异逐文件撤销本轮改动，不执行 reset 或 checkout。状态协议升级期间不自动覆盖旧计划；若回滚，删除新建的内部 v0.5 状态目录并恢复迁移前计划副本即可，业务设计和历史交付文档不受影响。
